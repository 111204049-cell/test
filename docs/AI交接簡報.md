# 腦圖書館：給其他 AI 的專案簡報

> 給人的使用說明（貼給 AI 時可刪掉這一段）
> - **第一部分**只有需求，不含任何技術選擇。想比較「不同 AI 會提出什麼方案」，只貼第一部分加第三部分。
> - **第二部分**是目前已做的實作、決定與限制。想請 AI 接手、審查或延續，再加貼第二部分。
> - **第三部分**是希望 AI 輸出的內容與規則。

## 第一部分：需求（與技術選擇無關）

### 1. 背景
使用者要做一套個人專屬的學習系統，名稱暫定「腦圖書館」。使用者同時在學大學課程、藝術、AI 等多個領域，想把課程影片、文件、筆記、單字和複習集中在同一個私人空間。使用者不是工程師，扮演產品負責人，由 AI 負責設計與寫程式。介面與溝通使用繁體中文。

### 2. 目標與限制
1. **跨平台**：要有網站，也要有手機 App（iOS 與 Android）。使用者的話：「手機我要 App 版本」。先個人試用，滿意再上架商店。
2. **高隱私**：只有本人能存取。A 帳號絕對看不到 B 帳號的任何資料。這不是公開影音平台。
3. **使用規模**：先當作 5 人以內，主要是使用者本人。
4. **成本**：長期零成本或極低成本。使用者有 Google Cloud 免費試用額度 $9,534，將於 2026/12/31 到期，之後不想產生高額帳單。使用者曾聽另一個 AI 說有「每月 $10 開發者福利」，**未經查證，不可當作事實**。
5. **介面品質**：好看、使用順暢。使用者的期待是「大家看到都覺得 wow，會得獎的那種」。使用者看過六種風格後偏向「液態玻璃」與「瑞士網格」的結合，但表示「還不到我的點」，尚未說明差在哪裡。
6. **語言**：先只做中文介面。
7. **希望提供新技術**：使用者希望 AI 主動提出更厲害、更新的做法，不只是保守方案。

### 3. 功能需求
1. **分類管理**：能依科目分類，例如「AI」「藝術」「大學」。大學底下還要分「大幾」，大幾底下才是各堂課。藝術、AI 學習等類別不是這個結構，所以層級要彈性。
2. **文字學習資料**：能建立並儲存文字類資料。
3. **匯入檔案**：可直接匯入 PDF、Word、PPT、網頁、圖片（圖片需文字辨識 OCR）來學習。
4. **筆記**：可以記筆記。
5. **螢光筆與標註**：文件資料可以畫螢光筆等標註。
6. **查單字**：點擊單字出現小視窗翻譯，主要是英文翻成中文。
7. **單字集**：可以收集單字成單字集。
8. **字典**：要有一個額外的字典。
9. **複習**：學科複習與單字複習都要有。複習的間隔曲線要符合大腦記憶與吸收新知的研究。可結合 AI。
10. **影片**：能儲存並播放大量教學影片。影片來源可能是使用者直接上傳，也可能是貼 YouTube 連結。
11. **首頁 AI 小助手入口**：首頁有一個像 AI 小助手的入口，使用者看到相關學習資料時可以隨手丟給它（文字、連結、截圖、檔案），它自動分類放到正確的科目。
12. **AI 供應商**：使用者目前在用 Claude、ChatGPT、Muse、Gemini。如果串進系統有幫助就用，之後可能把這個入口做成外掛（plugin）。
13. **開源資源**：使用者要求 AI 到 GitHub 搜尋「安全、且對達成需求有幫助」的開源專案，並說明選擇理由。

### 4. 明確不要
- 不要把大量影片放在需要付流量與儲存費的雲端空間。
- 不要讓使用者的資料與其他使用者混在一起可見。
- 不要把任何金鑰、密碼寫進公開的程式碼。

### 5. 尚未決定
- 介面風格的最終方向。
- 專案正式名稱。
- AI 供應商金鑰如何保管（每人自填，或由後端代為呼叫）。
- 是否上架 App Store 與 Google Play（iOS 開發者年費 $99 美元，Android 一次性 $25 美元）。

## 第二部分：目前的實作、決定與限制

### 1. 已做的決定與理由
| 決定 | 理由 |
|---|---|
| 先做 PWA（可安裝的網頁 App），不做原生 App | 一套程式碼、免費、不用審核；使用者要先試用 |
| React 18 + TypeScript + Vite | 一般性選擇，生態成熟 |
| Firebase：Authentication（Google 登入）、Firestore、Hosting | 免費 Spark 方案可用，不需要自己架後端 |
| 資料結構 `users/{uid}/nodes`、`users/{uid}/cards`，安全規則只允許本人讀寫自己的 `users/{uid}` | 達成資料隔離 |
| 影片放使用者自己的 Google Drive，只用 `drive.file` 權限加 Google Picker；資料庫只存連結 | 避開儲存與流量費，也避開 Google 敏感權限審核 |
| 科目用「深度不限、每層自訂名稱的資料夾樹」 | 因為各類別結構不同 |
| 複習用 FSRS 演算法（ts-fsrs） | 比傳統 SM-2 更貼近記憶研究 |
| 第一版 AI 只接 Gemini | 有免費層；Claude 與 ChatGPT 的 API 要付費 |
| 儲存層抽象為 `Store` 介面，有本機與 Firestore 兩種實作 | 登入前可「只存在這台裝置」，登入時可遷移本機資料 |

### 2. 技術與部署資訊
- 程式碼：GitHub `111204049-cell/test`，分支 `claude/intelligent-carson-2ddrms`。
- 網站：https://brain-6e0c0.web.app （Firebase Hosting）。
- Firebase 專案 ID：`brain-6e0c0`，Spark 免費方案，Firestore 位置 asia-east1。
- 部署：使用者在自己的電腦執行 `git pull` 與 `npm run deploy`（會部署網站與 `firestore.rules`）。AI 無法代為登入使用者的 Google 帳號，所以不能自行部署。
- 前端網頁用的 Firebase 設定（apiKey 等）是公開識別碼，已寫在 `src/firebase.ts`。

### 3. 已完成並在本機測過
- 科目資料夾樹與筆記（新增、改名、刪除、自動保存）。
- 單字卡與 FSRS 複習：翻面、四個評分、顯示各評分下次間隔、鍵盤 1 到 4、到期數徽章。
- 筆記「閱讀」模式點英文單字，顯示中文、音標、英文釋義，一鍵加入單字卡（自動附例句）；「編輯」模式選取文字查詢。字典用 Free Dictionary API，中文翻譯用 MyMemory，皆免費免金鑰。
- PWA：設定檔、圖示、離線快取、手機底部分頁。
- Google 登入與 Firestore 同步程式（含離線快取、第一次登入詢問是否上傳本機資料、同步錯誤提示列）。
- 介面：液態玻璃質感加瑞士大字體加單點紅色，淺色與深色模式跟隨系統。

### 5. 目前的已知問題（最重要）
**Google 登入後又回到登入畫面，尚未有任何一次登入成功。**
已排除並處理：
- 登入視窗空白：原因是離線快取（Workbox 的 navigateFallback）把 `/__/auth/handler` 當成 App 頁面攔截。已設 `navigateFallbackDenylist: [/^\/__\//]`。
- `redirect_uri_mismatch`：因為程式把登入網域設為目前網址 `brain-6e0c0.web.app`，而 Google OAuth 用戶端預設只登記 `firebaseapp.com`。需要使用者在 Google Cloud 加入 `https://brain-6e0c0.web.app/__/auth/handler`，**是否已加入尚待確認**。
仍未解決：從 Google 轉回後，應用程式沒有取得登入狀態。已改為在登入畫面顯示失敗原因與錯誤碼，等待使用者重新部署並回報。
可能的方向（均未驗證）：舊的離線快取仍在、登入網域與 OAuth 設定、第三方儲存空間限制、redirect 與 popup 流程差異。

### 6. 驗證限制（請勿高估）
- 開發環境無法連到 Firebase、YouTube 與字典服務，這些功能只用模擬資料測試過。
- 雲端同步、資料隔離、翻譯品質、手機安裝，**都沒有在真實服務與真實手機上驗證過**。
- 免費服務（MyMemory、Free Dictionary API、Gemini 免費層）的額度與品質可能變動，已知 Gemini 免費層自 2026 年起不再公開固定數字。

### 7. 已選用或評估過的開源專案
ts-fsrs（複習）、react-pdf-highlighter-extended（PDF 標註）、ECDICT（離線字典）、Transformers.js 加 Whisper（瀏覽器內語音轉文字）、Tesseract.js（OCR）、mammoth.js（Word）、Mozilla Readability（網頁）。篩選方式只是看星數、維護狀態與授權，**沒有逐一審查原始碼**。

## 第三部分：請你輸出的內容與規則

### 請輸出
請依序提供：
1. **整體架構建議**：用什麼技術與服務、為什麼，並與其他可行方案比較。
2. **資料模型**：主要資料表與欄位，以及如何達成使用者間的資料隔離。
3. **成本分析**：在免費或極低成本前提下，每個服務的額度與可能超出的情況。
4. **風險與取捨**：特別是影片、AI 金鑰保管、跨平台、免費額度。
5. **開發順序**：每一階段的內容、完成標準與驗證方式。
6. **你認為更好的新技術或做法**：並說明和保守方案的差異。
7. **（僅在有提供第二部分時）** 針對第二部分的已知問題給出診斷與修正步驟，並審查其中的決定。

### 規則
- 使用繁體中文。
- **不要編造**函式庫 API、服務價格、額度或授權；引用外部數字時，註明資料日期與來源，查不到就說不確定。
- 凡是你**沒有實際驗證**的結論，請明確標示「未驗證」。
- 不確定的需求先列出問題再往下做，一次最多問 5 題。
- 不要把金鑰、密碼、私密設定寫進程式或文件。
- 對使用者要用白話，不要假設使用者懂工程術語。
- 回答開頭先用 5 行以內說明你的核心結論。
